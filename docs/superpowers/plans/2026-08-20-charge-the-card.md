# Actually Charge the Card Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make booking creation place a real Stripe auth-hold on the renter's card, capture it on confirm, and release (cancel or refund) it on cancel.

**Architecture:** A new `PaymentsService` is the single file in the codebase that imports the `stripe` package — mirroring how `EmailService` is the only file that imports `nodemailer`. It exposes three verbs (`authorize`, `capture`, `release`) and deliberately does **not** catch Stripe errors; `BookingsService` owns the translation of those errors into HTTP exceptions at its three call sites. `Booking` gains one nullable column, `paymentIntentId`, holding the Stripe PaymentIntent id the booking owns.

**Tech Stack:** NestJS 11, Prisma 7 (`prisma-client` generator, output `generated/prisma`), PostgreSQL, `stripe` (Node SDK v22, ships its own TypeScript types), Jest 30 + ts-jest with hand-rolled mocks (no `Test.createTestingModule` anywhere in this repo).

**Spec:** `docs/superpowers/specs/2026-08-20-charge-the-card-design.md`

## Global Constraints

- **Ruling 3 — no swallowed errors, no fallback path.** `PaymentsService` never wraps a Stripe call in `try/catch`. It never null-checks `STRIPE_SECRET_KEY`. An empty/missing key is passed to the Stripe constructor as-is and fails at the first real API call, not at boot. Do **not** copy `EmailService`'s "log and return when unconfigured" pattern.
- **Ruling 5 — a payment failure blocks the operation entirely.** No booking row is written without a successful auth-hold. No booking becomes `confirmed` without a successful capture, and none becomes `cancelled` without a successful release. In `updateStatus`, the Stripe call happens **before** `prisma.booking.update`, so a failure means neither the DB update nor the `notifications.notify` call runs.
- **Ruling 4 — no idempotency keys.** Leave the deferral as a `ponytail:` comment on `PaymentsService` naming the upgrade path.
- **Ruling 2 — payouts are out of scope.** Do not touch `payoutStatus` logic, do not add Connect accounts, do not add a payout job.
- Exact user-facing messages, verbatim: `'Card was declined'`, `'Payment could not be captured'`, `'Payment could not be released'`.
- Amount conversion happens in exactly one place, inside `PaymentsService.authorize`: `Math.round(amount.toNumber() * 100)`.
- `src/app.module.ts` is **not** modified. `PaymentsModule` is reached only via `BookingsModule`'s import.
- Existing behaviour in `bookings.service.spec.ts` (the 4 notification tests) must keep passing. The only permitted edits to them are mechanical: adding the third constructor argument, and adding `paymentIntentId` to the shared booking fixture. No assertion changes.

Create `src/payments/payments.service.ts`:

```ts
import { Injectable } from '@nestjs/common';
import { ConfigService } from '@nestjs/config';
import Stripe from 'stripe';
import { Prisma } from '../../generated/prisma/client';

// ponytail: no idempotency keys on these calls (Ruling 4). A retry-safe key
// needs to be derivable before the Booking row exists; derive one from
// `${renterId}:${listingId}:${startDate}:${endDate}` if retry-safety is ever
// needed.
@Injectable()
export class PaymentsService {
  private readonly stripe: Stripe;

  constructor(private readonly config: ConfigService) {
    // Ruling 3: no `if (!key)` guard and no fallback branch. `?? ''` is a
    // type coercion only — an empty key is a string Stripe accepts at
    // construction and rejects at the first real API call, which is exactly
    // the "fail at the point of an actual charge, not at boot" behaviour we
    // want. Never swallow or log-and-continue here the way EmailService does.
    this.stripe = new Stripe(this.config.get<string>('STRIPE_SECRET_KEY') ?? '');
  }

  // Places an auth-hold. Stripe errors (StripeCardError included) propagate
  // to the caller untouched; BookingsService owns the HTTP translation.
  async authorize(
    processorPaymentMethodId: string,
    amount: Prisma.Decimal,
    currency = 'usd',
  ): Promise<string> {
    const intent = await this.stripe.paymentIntents.create({
      // The only place in the codebase that knows Stripe's minor-unit
      // convention: Decimal dollars -> integer cents.
      amount: Math.round(amount.toNumber() * 100),
      currency,
      payment_method: processorPaymentMethodId,
      capture_method: 'manual',
      confirm: true,
      // The renter isn't present at booking-request time to complete a 3-D
      // Secure challenge; off_session tells Stripe to use whatever
      // authentication the saved payment method already carries.
      off_session: true,
    });
    return intent.id;
  }

  async capture(paymentIntentId: string): Promise<void> {
    await this.stripe.paymentIntents.capture(paymentIntentId);
  }

  // One method, two Stripe calls depending on state, so callers don't need
  // to know whether the hold was already captured.
  async release(paymentIntentId: string): Promise<void> {
    const intent = await this.stripe.paymentIntents.retrieve(paymentIntentId);

    if (intent.status === 'requires_capture') {
      await this.stripe.paymentIntents.cancel(paymentIntentId);
      return;
    }

    if (intent.status === 'succeeded') {
      await this.stripe.refunds.create({ payment_intent: paymentIntentId });
    }
  }
}
```

**Type consistency:**

**Judgment calls made where the spec was silent** (each is annotated in the code above):
1. **Card-decline detection** is `(err as { type?: string })?.type === 'StripeCardError'`, not `instanceof Stripe.errors.StripeCardError`. The `instanceof` form would force `bookings.service.ts` to import `stripe` (breaking "PaymentsService is the only importer") and would not survive `jest.mock('stripe')`. The defensive-property-read style matches the existing `isExclusionViolation` helper in the same file.
2. **`?? ''` on the secret key** is a TypeScript coercion for `ConfigService.get<string>`'s `string | undefined` return, not a fallback branch. Behaviour under a missing key is unchanged from Ruling 3: the first API call throws.
3. **A booking with `paymentIntentId === null`** (a pre-migration row) is treated as an un-capturable/un-releasable payment and blocks the transition with the same `ConflictException`, rather than silently transitioning. Silently transitioning would be exactly the swallowed-fallback Ruling 3 forbids.
4. **`release` no-ops** for statuses other than `requires_capture` / `succeeded` (e.g. already `canceled`) — the spec names only the two branches, and a no-op is the only non-destructive reading of the rest.
5. **`{ cause: err }`** is attached to both `ConflictException`s so the underlying Stripe error stays in the stack trace. Translating an error is not swallowing it; discarding it would be.
6. **`@types/stripe` is not installed** — it is a deprecated stub for stripe v6 and the modern `stripe` package ships its own declarations.
